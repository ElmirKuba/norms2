## 1. Что вообще есть в проде

База (Postgres 16) — **10 МБ**, `content/` — 240 КБ. Дамп в сжатом виде ~300 КБ. Это не оговорка
и не «пока мало»: продукт [не хранит ПДн](./152fz.md) — ни ФИО, ни телефонов, ни почты. В базе
логин, псевдоним, **хеш** пароля, часовой пояс и пользовательская история (привычки, задачи, цели,
микро-победы, «держусь»).

Незаменимо здесь **не количество, а смысл**: для живых людей это их серии и прогресс. Восстановить
их неоткуда — исходников у пользовательской истории не бывает.

## 2. Что берём и что НЕ берём (реш. Elmir 31.07.2026)

| Берём | Почему |
|---|---|
| **Дамп БД** (`pg_dump`, plain SQL) | вся пользовательская история; ~420 КБ |
| **`content/avatars/`** | картинки загрузили сами люди, в git их нет |
| прод-`.env` — **только зашифрованным** | пароль БД и JWT-секреты; пока НЕ в бэкапе, см. §6 |

| НЕ берём | Почему |
|---|---|
| `docker/volumes/pg_data_prod` (65 МБ) | копия каталога работающего Postgres — **рваный снимок**: сервер пишет во время копирования, журнал не совпадает со страницами. Физическая копия делается либо с остановкой, либо через `pg_basebackup`. Плюс она привязана к мажорной версии (16.x) и вчетверо больше служебного мусора: индексы, карты видимости, свободное место |
| `content/notifications/*.md` | **проверено побайтно 31.07.2026**: все ноты идентичны файлам в `nest/seed-content/notifications/`, сид разложит их сам. Отметки «прочитано» лежат в БД (`notification_reads`) и уже в дампе |
| `docker/volumes/letsencrypt` | сертификаты Let's Encrypt перевыпускаются автоматически на новом хосте (реш. Elmir). Цена решения: у LE недельный лимит на повторные выпуски — при серии восстановлений подряд можно временно остаться без HTTPS |
| `sessions`, `session_token_history` | попадают в дамп (отдельно вычищать дороже, чем хранить), но ценности не имеют: люди просто войдут заново. Это больше половины строк базы |

**Сироты на томе:** `release-2.6.0/2.6.1/2.6.2.md` лежат в прод-`content/`, но в `notifications`
на них нет ни одной строки и из приложения их не открыть — остались после консолидации линии 2.6.
В бэкапе не нужны; в репозитории есть в истории git.

## 3. Процедура (ручная, по запросу)

Claude выполняет по SSH (`root@139.100.225.195`, ключ `~/.ssh/norms_johanna`), затем скачивает
архив **на рабочий стол мини-ПК** (`~/Desktop/`) — пока так, по решению Elmir.

```bash
# 1. На сервере: собрать в /home/backup (рядом с /home/norms2), с заменой прошлого содержимого
mkdir -p /home/backup
docker exec norms2_postgres_prod pg_dump -U norms2 -d norms2 --clean --if-exists \
  > /home/backup/norms2-db.sql          # сервис НЕ останавливаем: pg_dump берёт снимок в транзакции
rm -rf /home/backup/content && cp -a /home/norms2/docker/volumes/content /home/backup/content

# 2. Метка в README.txt рядом: дата UTC, VERSION, коммит, команда восстановления

# 3. Архив в /home (максимальное сжатие), старый одноимённый удаляется
zip -9 -r -q /home/norms2-backup-$(date +%Y%m%d-%H%M).zip backup

# 4. Скачать на мини-ПК
scp -i ~/.ssh/norms_johanna root@139.100.225.195:/home/norms2-backup-*.zip ~/Desktop/
```

`zip`/`unzip` доустановлены на сервере 31.07.2026 (их там не было).

## 4. Проверки — обязательная часть, а не формальность

Бэкап без проверки — это файл-надежда. После каждого снятия:

1. `unzip -t` на сервере **и** на мини-ПК — архив не побит;
2. `sha256sum` совпадает с обеих сторон — при скачивании ничего не потерялось;
3. заглянуть внутрь дампа: число `CREATE TABLE`, число блоков `COPY`, **число аккаунтов** сходится
   с живой базой, файл не оборван на середине.

## 5. Восстановление

```bash
unzip norms2-backup-ГГГГММДД-ЧЧММ.zip
docker exec -i norms2_postgres_prod psql -U norms2 -d norms2 < backup/norms2-db.sql
cp -a backup/content/avatars/. /home/norms2/docker/volumes/content/avatars/
```

Дамп идёт с `--clean --if-exists`: он сам сносит существующие объекты перед заливкой. На живом
проде это **разрушительная операция** — запускать только осознанно.

> ⚠️ **Восстановление ни разу не проверялось на практике** (на 31.07.2026 сверялась только
> структура файла). Гипотезу нужно проверить: развернуть дамп в пустую базу на dev и убедиться,
> что данные на месте. До этого момента честная формулировка — «дамп выглядит целым», а не
> «бэкап работает».

## 6. Открытые дыры (осознанные, не забытые)

1. **Копия одна и на том же столе, что и всё остальное.** Правило «три копии, два носителя, одна
   вне дома» не выполняется — сейчас копий фактически одна.
2. **Архив не зашифрован.** Внутри псевдонимы и хеши паролей. На рабочем столе лежать может;
   в облако, на флешку или в git в таком виде — нельзя.
3. **Прод-`.env` не сохранён нигде, кроме самой Johanna.** Проверено 31.07.2026: в
   `~/secrets-archive/env/norms2.env` лежит **dev**-версия (есть `PGADMIN_*`, нет
   `JWT_REFRESH_SECRET`). Потеря не смертельна — секреты можно сгенерировать заново, все сессии
   при этом разлогинятся, — но восстановление превращается в «вспомни, что там было».
4. **Ключ `norms_johanna` существует в одном экземпляре** (диски мини-ПК). Отказ диска = потеря
   доступа к серверу. Это про доступ, не про данные, но дыра в том же ряду.
5. **Автоматизации нет.** Бэкап снимается только когда Elmir попросит; между запросами прод не
   защищён ничем.

## 7. Когда менять инструмент

`pg_dump` не масштабируется: он читает базу одним потоком, а при восстановлении **заново строит все
индексы**. На терабайте это не «большой файл», а десятки часов простоя. Плюс дамп — снимок одного
момента: всё, что случилось между снимками, теряется.

Куда двигаться, когда вырастем:

| Размер базы | Чем бэкапить |
|---|---|
| до ~10 ГБ | `pg_dump` — то, что делаем сейчас |
| 10–100 ГБ | параллельный `pg_dump -Fd -j` либо уже `pgBackRest` |
| выше | физическая базовая копия + **непрерывный архив WAL**, восстановление на точку во времени (PITR) |

Смысл перехода: базовая копия снимается раз в неделю, а между ними уезжает только журнал
предзаписи — его объём пропорционален **изменениям за сутки, а не размеру базы**. Это же лечит то,
чего дамп не умеет: «в 14:32 выкатили миграцию, снёсшую таблицу» → откат на 14:31.

Отдельно: **реплика — не бэкап.** Она повторит и ошибочный `DELETE` через секунду. Реплика про
доступность, бэкап — про «мы всё испортили и хотим вчера».

**Триггер пересмотра:** база перевалила за **1 ГБ** или живых пользователей стало больше **сотни**
— заводим ADR и ставим `pgBackRest`/`WAL-G` с выгрузкой в объектное хранилище. Переход
эксплуатационный: схема, код и приложение не меняются.
