# ADR-0063: «Акцент» — без LLM в критическом пути

- Статус: принято (2026-07-31, фаза 2, подфаза 2.7 · блок I, реш. Elmir) — **обратимо в сторону
  добавления** (ИИ можно включить как опциональный слой, не трогая существующее).
- Контекст: у проекта нет гарантированного бюджета на токены внешних моделей и нет GPU на
  прод-VDS. Вопрос возник при обсуждении `Recommender` (подфаза 2.8): «подбирать действия под
  состояние» звучит как задача для LLM. Разбор показал обратное — для этой задачи правила лучше,
  а там, где LLM действительно полезен, он не обязан быть в критическом пути.

  Формально это уже следовало из [`api-contracts §14`](../sections/accent/api-contracts.md)
  («AI-эндпоинты — волна 2.13+, не в MVP»), но нигде не было записано **как правило**, которое
  нельзя нарушить, соблазнившись удобством.

## Решения

1. **Ни одна функция раздела не деградирует при отсутствии ИИ.** Это главный инвариант. Проверка
   простая: отключи всё, что связано с моделями, — продукт обязан остаться целым, а не «работать
   без подсказок».

2. **`Recommender` (2.8) — rule-based, детерминированный.** Все входы уже есть в данных:
   состояние из чек-ина, `energyCost` и `disabledForStates` у микро-побед, история выполнений,
   время суток, просроченные задачи, ближайшие вехи, откаты лесенки, частота столкновений с
   препятствиями. Подбор — взвешенный скоринг из десятка правил (низкая энергия → только
   `energyCost=1`; вечер и серия под угрозой → минимальная версия привычки; веха завтра → она
   вперёд). Мгновенно, воспроизводимо, без сетевых вызовов.

3. **Объяснимость — преимущество правил, а не их недостаток.** Правило честно говорит «предлагаю
   это, потому что ты отметил низкую энергию и раньше делал это в такие дни». LLM такого не
   гарантирует, а требование объяснимости для AI-эндпоинтов у нас уже записано (`api-contracts §14`:
   «не стыдить, не обещать лечение, объяснимость»). В разделе про anti-burnout непрозрачная
   рекомендация хуже отсутствия рекомендации.

4. **Обучение — без ML.** Частотная статистика «предложено → сделано» на аккаунт плюс
   epsilon-greedy (в ~10% случаев показываем не топовое, чтобы выдача не схлопнулась в один
   вариант). Это десятки строк кода, ноль библиотек, ноль расходов — и этого достаточно, потому что
   пространство вариантов у одного человека мало (десятки микро-побед, не миллионы товаров).

5. **LLM оправдан только на текстовой работе** — разбить размытую цель на шаги, переформулировать
   срыв в опыт (`decompose-goal`, `repack-after-relapse`). Живёт **за фича-флагом**: есть ключ —
   кнопка появилась, нет ключа — кнопки просто нет. Никакая другая функция от флага не зависит.

6. **Приватность — главный аргумент, а не деньги.** Отправка формулировок целей, заметок о срывах
   и описаний препятствий во внешний API — это передача пользовательского контента третьей стороне.
   Против принципа self-hosted и против всей логики минимизации данных
   ([ADR-0001](./0001-data-minimization-no-pii.md)). Даже при неограниченном бюджете внешний вызов
   требовал бы явного согласия человека на конкретный текст, а не общей галочки.

7. **Локальный инференс — только дев-режим.** На машине разработчика 8 ГБ VRAM, туда влезает
   квантованная 7–8B через llama.cpp. На прод-VDS видеокарты нет, CPU-инференс для интерактивных
   сценариев неприемлем → для пользователей это не масштабируется. Значит локальная модель может
   помогать в разработке (черновики текстов, наполнение паков), но не может быть частью продукта.

## Рассмотренные альтернативы (ToT)

- **A. LLM как ядро рекомендаций** (модель смотрит на состояние и предлагает действия) — отвергнута:
  непрозрачно, платно на каждый показ экрана, недоступно офлайн, и главное — требует отправлять
  наружу дневниковые данные при каждом открытии дашборда.
- **B. Гибрид: правила + LLM для «сложных случаев»** — отвергнута: «сложный случай» пришлось бы
  определять правилами, то есть работа всё равно делается дважды, а поведение продукта становится
  недетерминированным именно там, где человеку тяжелее всего.
- **C. Локальная модель на проде** — отвергнута по железу (см. п.7); вернуться можно, если VDS
  когда-нибудь получит GPU, но проектировать под это нельзя.
- **D. Правила + опциональный LLM за флагом на текстовых задачах** — **выбрано.**

## Последствия

- `Recommender` 2.8 проектируется как набор правил со скорингом; в его нарезке должен появиться шаг
  «объяснение выбора» — текст «почему предложено» строится из сработавших правил.
- Появление ИИ-функций не блокирует ни одну подфазу: они аддитивны и выключаемы.
- Если внешний ИИ когда-нибудь включат, потребуется отдельное решение по согласию на передачу
  текста (ADR-0001) — эта задача не считается решённой настоящим ADR.
- Связано: [[0049-accent-product-principles]] (внешняя память + самокомандование — правила это
  усиливают, а не подменяют), [[0001-data-minimization-no-pii]], [[0062-accent-obstacles-model]]
  (журнал столкновений как источник входов для правил), `api-contracts §14`.
