# ADR-0061: Свежесть данных между устройствами без WebSocket (refetch по фокусу + ревизия)

- Статус: принято (2026-07-29, фаза 2, патч 2.6.4 · сквозная инфра, реш. Elmir) — **обратимо**
  (аддитивный слой; при необходимости поверх той же ревизии включается SSE).
- Контекст: SPA держит данные в Signals и перечитывает их только при навигации/действии. Один
  пользователь работает с **нескольких устройств** (телефон + десктоп) и в нескольких вкладках.
  Догфудинг Elmir (2026-07-29, прод 2.6.3): привычка «Приседания» отмечена с телефона — на десктопе
  вкладка продолжает показывать её как невыполненную до ручного F5.

  Проблема не только косметическая. Живая проверка на dev (2026-07-29, `staleverify`, quantitative
  «Приседания», target 100) показала:
  - **лесенка защищена** — `updateIfOpen` (атомарный условный UPDATE, [ADR-0035]) двигает планку
    только на переходе из открытого статуса; повторный `complete` и гонка 5× дали `ladderEvent=null`
    и ноль 5xx;
  - **но фактическое значение затирается молча** — `complete` со «стейл»-вкладки перезаписал
    `doneValue 100 → 60`, а статус `done → partial`. Победил последний писатель, потери не видно
    ни серверу, ни человеку.

  То есть нужны два разных лекарства: клиент должен **узнавать** о чужих изменениях, а сервер —
  **не принимать** операцию, построенную на устаревшем представлении.

## Решения

1. **Основной триггер обновления — возврат внимания к вкладке, а не таймер.** Слушаем
   `document.visibilitychange` (вкладка стала видимой), `window.focus` и `online`. Постоянного
   опроса нет: пока вкладка в фоне, трафик нулевой. Это покрывает ровно тот сценарий, который болит
   («переключился с телефона на комп»), и ничего не стоит в простое.

2. **Дешёвая проверка «а изменилось ли вообще» — ревизия аккаунта.** `GET /accent/rev` →
   `{ rev: { habits, goals, microWins, antiHabits, obstacles, … } }` — посекционные счётчики.
   Фронт при триггере дёргает только его (десятки байт, один индексный запрос) и перезагружает
   **только те экраны, чья секция изменилась**. Не совпало ничего — не делаем ни одного тяжёлого
   запроса.

3. **Ревизию инкрементит инфраструктурный слой, а не домены.** Порт `RevisionBumperPort`
   (`bump(accountId, section)`) + NestJS-интерсептор на мутирующих маршрутах `/accent/*`: успешный
   `POST/PATCH/PUT/DELETE` → `UPDATE accent_revisions SET rev = rev + 1`. Доменные сервисы о ревизии
   не знают (иначе счётчик пришлось бы вкручивать в каждый use-case и не забывать при добавлении
   новых). Секция выводится из первого сегмента пути.

4. **Тихое обновление, а не «дёрганый» экран.** Рефетч идёт без спиннера, результат применяется
   точечным патчем сигналов (как `_patchTask`). Обновление **откладывается**, если пользователь
   занят: открыт `MatDialog`, есть незавершённая мутация, идёт таймер, форма «грязная». Координатор
   держит счётчик «занятости» и выполняет отложенный рефетч, когда занятость снята.

5. **Между вкладками одного браузера — `BroadcastChannel`, без сервера.** Вкладка, сделавшая
   мутацию, вещает `{ section }`; остальные помечают секцию устаревшей и обновляются (сразу — если
   видимы, иначе при фокусе). Ноль запросов к бэку на кросс-табный случай.

6. **Второй слой — optimistic `version` на `tasks` (реш. Elmir).** Свежесть UI уменьшает окно
   конфликта, но не закрывает его (можно кликнуть за миг до рефетча). Поэтому задача получает
   колонку `version` и правится по CAS ([ADR-0035](./0035-concurrency-control.md), как `accounts` и
   `anti_habits`): клиент шлёт `version`, который он видел на экране; `UPDATE … WHERE id=… AND
   version=…` не нашёл строку → операция **не применена**, ответ `409 TASK_VERSION_CONFLICT` с
   актуальной задачей в теле. Стейл-вкладка физически не может затереть чужое значение.

   **Почему CAS, а не «409 на любой повторный `complete`»:** повтор сегодня используется легально —
   таймер `timed`-привычки шлёт **накопленное** значение (`сделано + прошедшее`), а «Начать сначала»
   **заменяет** прогресс на меньшее ([ADR-0057], habits.component). Эти клиенты знают актуальное
   состояние, поэтому их `version` совпадает и запись проходит; стейл-вкладка держит старый
   `version` и получает 409. Различение по факту «задача уже закрыта» такого разделения не даёт.

   **Дисциплина bump'а:** `version + 1` во всех путях правки задачи (complete / uncomplete /
   postpone / skip / patch) — все они идут через один репозиторий, там и инкрементим.

   **UX конфликта — без «обновите страницу».** Фронт на 409 берёт актуальную задачу из тела ответа,
   молча патчит карточку и показывает мягкое «уже отмечено на другом устройстве — обновили». Красная
   ошибка — только там, где нужно решение человека (записанное значение расходится с тем, что он
   вводил). Требовать F5 нельзя: устранение F5 — и есть цель этого патча.

7. **Троттлинг и бюджет:** не чаще одной проверки ревизии в 10 с на вкладку; данные, полученные
   менее 5 с назад, считаются свежими и не перезапрашиваются.

8. **Рассмотренные альтернативы (ToT):**
   - **A. WebSocket-канал** — отвергнут сейчас: постоянное соединение на каждого клиента, свой
     lifecycle (реконнекты, heartbeat, аутентификация сокета), правки nginx и прод-конфига. Цена
     инфраструктуры несоразмерна задаче «узнать, что я сам сделал на другом устройстве». Вернёмся к
     нему, когда появится **мессенджер** (фазы 6–7), где push действительно обязателен.
   - **B. SSE (`EventSource`)** — дешевле WS, но всё равно держит открытое соединение на вкладку и
     требует серверного фанаута. Отложен: становится оправдан, если появится потребность в
     обновлении без фокуса (совместные челленджи, соц-волна 2.13+). Поверх уже готовой ревизии
     включается локально, без переделки клиента.
   - **C. Периодический polling списков (каждые N сек)** — отвергнут: платим постоянно и в фоне за
     событие, которое случается редко.
   - **D. `ETag`/`If-None-Match` + 304 на списках** — отвергнут как основной механизм: экономит
     трафик, но сервер всё равно собирает представление, чтобы посчитать ETag; ревизия дешевле по
     CPU и покрывает сразу все секции одним запросом. Не противоречит — может быть добавлен позже.
   - **E. Только серверный конфликт-контроль, без клиентского обновления** — отвергнут: чинит
     потерю данных, но оставляет человеку заведомо врущий экран.
   - **G. Монотонность прогресса** (`doneValue = max(старое, новое)`, для `clock` — `min`; уменьшение
     только с явным `replace`) — отвергнута как основной механизм: бесшовна, но **молча
     игнорирует ввод** (ввёл 60 — осталось 100) и делает «правду» зависимой от истории записей;
     флаг `replace` остаётся лазейкой для стейл-клиента. Может вернуться как UX-надстройка над CAS
     (при 409 предложить «записать большее значение?»).
   - **H. `Idempotency-Key`** — не решает задачу: защищает от повтора **одной и той же** операции
     (ретрай сети), а стейл-вкладка присылает свою, с другим ключом.
   - **F. Фокус-рефетч + ревизия + CAS по `version` (слои 1–7)** — **выбрано.**

## Уточнение 2026-07-31 (перед стартом реализации)

Решения 1–5 и 7 в силе. **Пункт 6 (optimistic `version` на `tasks` + CAS) заменён более узким
механизмом**, и вот почему: к моменту реализации стало известно, сколько существует легальных
повторных `complete`. Их ровно два, и оба отличимы от стейл-повтора по **направлению** значения:

- накопительный таймер шлёт **больше** (было 5, стало 9);
- «Начать сначала» шлёт **меньше**, но осознанно;
- стейл-вкладка шлёт **меньше** неосознанно.

Значит достаточно требовать **явного намерения на понижение** (`replace: true`, который шлёт только
«Начать сначала»); всё остальное понижение — `409` с актуальной задачей в теле. Это одна правка в
домене вместо версии строки на пяти таблицах с прокидыванием во всех путях правки.

Дополнительный довод против CAS здесь: `version` — версия **всей строки**, а конфликтует одно поле.
Перенос задачи на завтра в соседней вкладке давал бы `409` на отметку выполнения, хотя `doneValue`
никто не трогал; такие ложные конфликты быстро приучают слать версию не глядя, и защита вырождается
в ритуал.

**Ревизия (`GET /accent/rev`, решения 2–3) отложена во вторую часть патча** — вместе с дашбордом.
Она экономит запросы при нагрузке, которой пока нет (десятки записей на аккаунт), и добавляет запись
в БД на каждой мутации. Первая часть обходится обновлением по фокусу без ревизии.

К CAS вернуться, если появятся совместные сущности (соц-волна 2.13+) или гонка повторится там, где
направление значения не различает намерение.

## Последствия

- Появляется таблица/строка ревизий на аккаунт (`accent_revisions`, jsonb или колонки по секциям) и
  один эндпоинт `GET /accent/rev`; мутации получают +1 дешёвый UPDATE.
- На фронте появляется общий `DataFreshnessService` (core, а не accent) — экраны регистрируют
  `{ section, reload }` и перестают заботиться о том, когда обновляться.
- `tasks` получает колонку `version` (аддитивная миграция, `default 1`) и правится только по CAS;
  контракт `POST /accent/tasks/:id/complete` получает поле `version` в теле и новый исход `409` —
  ломающее изменение поведения (раньше повтор молча перезаписывал), фиксируется в `api-contracts §5`.
- Все будущие разделы (препятствия 2.7, чек-ин 2.8, недельный слой 2.10) подключаются к готовому
  механизму одной регистрацией секции — поэтому патч идёт **до** 2.7.
- Связано: [[0035-concurrency-control]] (CAS/optimistic — тот же принцип «не пиши поверх чужого»),
  [[0019-backend-architecture-conventions]] (серверная агрегация), [[0049-accent-product-principles]]
  (экран не должен врать человеку), `docs/sections/accent/api-contracts.md`.
