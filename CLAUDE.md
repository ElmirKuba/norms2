## Стек и архитектурные принципы

- **Frontend:** Angular 17+, standalone-компоненты, Signals, **чистый SCSS/CSS** (свои компоненты, без Tailwind). SPA. **Angular Material — только `MatDialog`** (модалки), см. [`docs/decisions/0025-ui-ux-design-language.md`](./docs/decisions/0025-ui-ux-design-language.md).
- **Backend:** NestJS, **5-слойная архитектура** ([ADR-0030](./docs/decisions/0030-stack-revision-drizzle-5layer-npm.md), образец — `~/coding/kuba-game`): `controllers → use-cases → domain-services → adapters → repositories`. Раскладка — **feature-first**: фичи в `modules/<feature>/` (без ORM), ORM-слой (схемы+репозитории) вынесен в `database/`, инфра в `system/`+`shared/` ([ADR-0034](./docs/decisions/0034-feature-first-layout.md)). Поток: controller→use-case→domain-service→adapter→repository. **Кросс-доменные вызовы только ВНИЗ:** use-case области A зовёт domain-service ДРУГОЙ области B (не её use-case) → круговой DI исключён. Замена доступа к данным — без правки бизнес-слоёв.
- **БД:** PostgreSQL + **Drizzle** ORM ([ADR-0030](./docs/decisions/0030-stack-revision-drizzle-5layer-npm.md); НЕ TypeORM). Репозитории — слой `repositories`; домен/use-cases про ORM не знают.
- **Идентификаторы (сквозная конвенция, всегда):** PK и все FK — строка формата `uuidv7___unixmillis` (пример `019e7488-0147-7305-9b95-a553f2d00c8e___1780071500548`). Генерация — общий util `generateId()` на бэке и фронте. Подробно — [`docs/decisions/0016-primary-key-format.md`](./docs/decisions/0016-primary-key-format.md). Применяется ко всем таблицам/сущностям во всех фазах.
- **ORM:** Drizzle + drizzle-kit (явные миграции, без auto-push в проде). Слой `repositories` инкапсулирует ORM.
- **Пакетный менеджер:** npm ([ADR-0030](./docs/decisions/0030-stack-revision-drizzle-5layer-npm.md); не pnpm).
- **Docker** для всего (dev + prod), **Let's Encrypt** для TLS, **SSH + Git** для деплоя.
- **Хостинг:** на время разработки РФ допустим, домен `нормисы.рф`; переезд вне РФ — под давлением (см. [`docs/decisions/0023-deployment-jurisdiction.md`](./docs/decisions/0023-deployment-jurisdiction.md)). Щит приватности — отсутствие ПДн, не локация.

### Слоистая архитектура backend (строго)

**Раскладка — feature-first + вынесенный `database/`** ([ADR-0034](./docs/decisions/0034-feature-first-layout.md)):

```
src/
  modules/<feature>/   # вертикальный слайс БЕЗ ORM: controllers/ use-cases/
                       #   domain-services/ adapters(порты)/ interfaces/ dtos/ <feature>.module.ts
  database/            # вся связь с Drizzle: client/ schemas/ relations/ repositories/<feature>/
  system/              # инфра без ORM: config, logging
  shared/              # filters, utility-level, общие interfaces
  app.module.ts · main.ts
```

**5 слоёв** ([ADR-0030](./docs/decisions/0030-stack-revision-drizzle-5layer-npm.md)) — поток вниз: `controllers` → `use-cases` (точка кросс-домена) → `domain-services` → `adapters` (порты: интерфейсы+DI-токены, в фиче) → `repositories` (Drizzle-реализации, в `database/`). ORM импортируется **только** в `database/` (schemas+repositories); доменные слои его не видят. **Кросс-домен — только вниз:** use-case области A зовёт domain-service области B (не use-case B) → нет круговой DI. Архитектура = правила зависимостей, не раскладка файлов. Детали — [`docs/architecture.md`](./docs/architecture.md).

## Рабочий цикл

1. **Уточнить фазу.** Обзор фаз — [`Technical-assignment.md` §2](./Technical-assignment.md); прогресс и подзадачи текущей фазы — в её `docs/impl-phaseN-plan.md` (сейчас [`docs/impl-phase2-plan.md`](./docs/impl-phase2-plan.md)). Если фаза ещё не открыта — сначала закрыть предыдущие.
2. **Прочитать только нужные docs.**
3. **Внести изменения** — по шагам плана: обычно один шаг = один слой (`nest/` / `angular/` / `docs/`) = один коммит. При пошаговой работе это выходит само собой, и история читается по шагам. **Но дробить ради слоёв не обязательно** (реш. Elmir 2026-07-30): если накопился единый смысловой скоуп (одна тема задела и код, и доку — заход аналитики, сквозная правка, закрытие блока), коммитить скоупом можно.
4. **Обновить документацию,** если изменилось поведение, контракт или структура. Изменение API без обновления `docs/api-contracts.md` — не считается завершённым.
5. **Отметить в `impl-phaseN-plan.md`** текущей фазы, что пункт выполнен. Если по ходу появились новые подзадачи — дописать туда же. **Отложил что-то сознательно или наткнулся на незакрытое — строкой в [`docs/open-threads.md`](./docs/open-threads.md) сразу**, а не «запомню»: хвост, живущий только в переписке, теряется на следующем заходе.
6. **Запушить во все пять зеркал** — `origin` + `codeberg` + `sourcehut` + `gitflic` + `gitverse`, пятью отдельными командами (см. «[Куда пушим](#куда-пушим-пять-равноправных-зеркал-реш-elmir-2026-07-31)» ниже). Коммит, уехавший только на GitHub, оставляет зеркала расходящимися.

### Правило шага (реш. Elmir 2026-08-04)

Шаг плана — не «сколько успел», а **единица, которая держится сама**:

- **Самодостаточность.** Шаг **опирается на предыдущие, но не ждёт следующих**: после него дерево собирается, `tsc` зелёный, продукт работоспособен. Нельзя оставлять «допишу в следующем шаге» — если без продолжения ломается, это один шаг, а не два.
- **Коммит.** Каждый шаг — **минимум один коммит**, больше можно (внутри шага бывают отдельные смысловые куски). Ноль коммитов на шаг — нельзя.
- **Пуш.** После каждого шага — во все пять зеркал. Не «накоплю и залью»: незапушенный шаг существует только на этом диске.
- **Отметка.** В `impl-phaseN-plan.md` шаг отмечается выполненным **в том же коммите**, что и его содержимое, — тогда план не расходится с кодом даже на один коммит.

Почему так: заходы обрываются на лимите контекста, и всё, что не закоммичено и не отмечено, приходится восстанавливать по памяти следующему заходу — а он начинается с чистого листа.

## Дока отражает ФАКТ, а не только план (правило свежести)

Вся дока — `docs/`, ADR, `impl-*-plan.md`, **память** — должна описывать **то, чем проект является СЕЙЧАС по факту**, а не только «что будет».

- Пока чего-то **нет** — пишем в будущем времени («будет», «планируется», статус 📋/⬜).
- Как только это **появилось в коде** — в тот же заход переписываем на **настоящее** время («является», «реализовано», статус ✅): описываем не «что надо сделать / как будет выглядеть», а **что оно есть по факту**.
- Это касается и формулировок (будущее→настоящее), и статусов, и memory (`MEMORY.md` + файлы), и `impl-*-plan.md`.
- При каждом завершённом этапе кодинга: синхронизировать связанные доки/ADR/план/память с реальностью. Расхождение доки с кодом — это баг доки.

Подробности и примеры — [`docs/methodology.md`](./docs/methodology.md). Кратко, всегда:

1. **Chain-of-Thought** — перед нетривиальной правкой расписать шаги: что меняется → в каком слое → какие инварианты домена → что обновить в docs. Не можешь выписать цепочку — задача недопонята.
2. **Tree-of-Thoughts** — на архитектурной развилке генерировать 2–4 ветви, оценивать (слои / обратимость / 152-ФЗ / простота), отсекать. **Итог развилки обязан стать ADR** в [`docs/decisions/`](./docs/decisions/README.md) — иначе решение потеряно.
3. **Self-Consistency** — перед пометкой пункта `impl-phaseN-plan.md` как `[x]`/✅ для рискованного (контракты, миграции, правила доступа, 152-ФЗ) — перепроверить **другим путём**, не перечитыванием. Сошлось — уверенность; разошлось — найден баг.

Тривиальные правки (опечатки, переименования) — без этого ритуала.

## Отложенная работа: TODO-маркеры в коде

Если что-то **пока нельзя дописать** (зависит от ещё не сделанного этапа, ждёт решения и т.п.) — не молчать, а **оставить TODO-маркер прямо в коде**, чтобы не потерять:

```ts
// TODO: Claude Code: ГГГГ-ММ-ДД: текст что и почему отложено
/** TODO: Claude Code: ГГГГ-ММ-ДД: текст */
```

- Формат строго: префикс `TODO: Claude Code: ` + дата `ГГГГ-ММ-ДД` + суть. В line- или block-комментарии.
- **Когда появляется возможность** — пройтись по всем местам `grep -rn "TODO: Claude Code: "` и доделать/убрать. Перед закрытием этапа и при «нечего делать» — проверять этот список.
- Elmir тоже оставляет свои: `TODO: ElmirKuba: ...`. Он человек и может забыть — **периодически** (на старте этапа / при паузах) сканировать `grep -rn "TODO: ElmirKuba: "` и напоминать/подхватывать их.
- TODO — это **долг с адресом**, а не свалка: каждый должен быть конкретным и закрываемым; протухший/сделанный — удаляем.

## Куда пушим: пять равноправных зеркал (реш. Elmir 2026-07-31)

Код живёт **в пяти местах, все обновляются на каждый коммит**. Смысл не в сохранности кода (git
распределённый — полная история есть на мини-ПК, на прод-сервере и в каждом remote), а в
сохранности **доступа**: каждое зеркало закрывает свою ось отказа, а РФ-площадки — ещё и ту, что
не закрывает никто другой: «зарубежные сервисы недоступны из РФ».

```bash
git push origin main      # GitHub    — git@github.com:ElmirKuba/norms2.git (с него пулит прод)
git push codeberg main    # Codeberg  — ssh://git@codeberg.org/elmir_kuba/norms2.git
git push sourcehut main   # SourceHut — git@git.sr.ht:~elmir_kuba/norms2
git push gitflic main     # GitFlic   — git@gitflic.ru:elmirweb/norms2.git (ник там elmirweb)
git push gitverse main    # GitVerse  — ssh://git@gitverse.ru:2222/elmir_kuba/norms2.git (порт 2222)
```

- **Пять отдельных команд, а не одна.** Пульт с несколькими push-адресами (`git push mirrors`)
  проверен вживую 31.07.2026, когда лежал Codeberg: **git идёт по адресам по очереди и обрывается
  на первом же отказе** — до следующих не доходит вообще, код возврата 128. Один лежащий хостинг
  блокировал бы доставку во все, что стоят после него. Отдельными командами видно построчно, кто
  принял, а кто нет.
- **Отставшее зеркало — норма, а не авария.** Хостинги падают (Codeberg — регулярно, он
  некоммерческий и живёт на пожертвованиях). Не принял — доливаем позже той же командой, работа
  из-за этого не останавливается.
- `upstream` у `main` — `origin/main`, поэтому голый `git push` уходит **только на GitHub**;
  остальные — отдельными строками.
- **Прод (Johanna) пулит с GitHub** — пока что. Если GitHub станет недоступен, переключение =
  `git remote set-url origin ssh://git@codeberg.org/elmir_kuba/norms2.git` на сервере (или
  `git@git.sr.ht:~elmir_kuba/norms2`), ключ там свой; деплой в остальном не меняется
  ([`docs/deployment.md §5`](./docs/deployment.md)). Годится любое зеркало, которое приняло
  последний коммит, — сверить вершину перед переключением.
- **Ветку не переименовывать.** Подсказки GitFlic и GitVerse предлагают `git branch -M master` —
  не выполнять: переименование разъедет репу с остальными зеркалами и с прод-сервером. Ветку по
  умолчанию переставляем в настройках самой площадки.

### Три ветки с 14.08.2026 (реш. Elmir)

До 2.9.3 ветка была одна. Теперь их три, и у каждой своя работа:

| Ветка | Что это | Кто на неё коммитит |
|---|---|---|
| `main` | **состояние, которое покажем публике.** Заморожена на 2.9.3 по содержанию: сюда едут только правки, которые обязаны быть в презентуемой версии | правки блокеров анонса |
| `release-2.9.3` | ветка выпуска: то же, что `main`, но живёт отдельно, чтобы `main` можно было двигать, не трогая презентуемое | правки блокеров анонса |
| `developing-2.10` | **обычная разработка**, следующая подфаза | всё остальное |

- **Прод (Johanna) пулит `main`** — то есть на сервере продолжает жить презентуемое состояние, а
  работа в `developing-2.10` туда **не попадает до слияния**. Это не побочный эффект, а смысл
  разделения: пока права на результат не уточнены, боевой сервер не должен уезжать вперёд текста,
  который мы собираемся показать.
- **Правка блокера анонса — двойная обязанность:** положил на `release-2.9.3`/`main` — **слей в
  `developing-2.10`**, иначе следующая подфаза начнётся без неё и починка «потеряется вперёд».
- **Тег `v2.9.3` — не свойство ветки.** Тег указывает на **коммит**, и раз все три ветки выросли
  из одного, он одинаково достижим из любой: отдельных тегов «в main», «в 2.9.3» и «в 2.10» не
  бывает и не нужно. Пушится один раз на каждое зеркало: `git push <remote> v2.9.3`.
- **Пуш веток — те же пять команд на каждую.** Незапушенная ветка существует только на этом диске,

## Где НЕ должно быть кода

- ❌ Бизнес-логика в `app.module.ts` или `main.ts` — только bootstrap.
- ❌ Переменные окружения в коде — только через `ConfigService`, описаны в [`docs/deployment.md`](./docs/deployment.md).
- ❌ Импорт ORM (`drizzle`) в use-case/доменных слоях — только через adapters/repositories.
- ❌ **Зависимость бизнес-слоёв от КОНКРЕТНЫХ инфра-реализаций.** Чистые границы (строго): controllers/use-cases/domain-services зависят **только от портов/абстракций** (интерфейс + DI-токен), НЕ от конкретных классов инфры (`DatabaseService`, репозитории, drizzle-типы, `$inferSelect`, схемы). Транзакции — через опаковый `Transaction`/`TransactionRunner`, не через сырой Drizzle-tx. **Конкретику знают только** `database/*` и `*.module.ts` (composition root — он связывает токен↔реализацию, это норма). Периодически **grep-аудитить границу** (`from 'drizzle-orm`, `from 'pg'`, `database/`, `$inferSelect`, `DrizzleExecutor` вне `src/database/`): компилятор такие утечки не ловит (типы совпадают), а домен должен оставаться заменяемым без касания.
- ❌ Drizzle auto-push в проде — только явные миграции (drizzle-kit).
- ❌ **`docker restart` для dev-контейнеров.** Перезапуск — только `make dev-restart` (или `dev-down` + `dev-up`): он пересоздаёт контейнер, а `docker restart` сохраняет его файловую систему вместе с протухшим `tsconfig.build.tsbuildinfo` — инкрементальная сборка тогда рапортует «Found 0 errors», не эмитит `dist`, и бэк падает с `Cannot find module '/app/dist/main'` при внешне живом контейнере. Диагноз неочевиден: логи зелёные, `curl` молчит.
- ❌ **Состояние «спрятано» без выхода обратно.** Завёл флаг архива — назови экран, где человек его увидит, и способ вернуть. Не можешь — не заводи флаг.
  - **Проверяется машиной:** `make audit-states` ([`scripts/audit-storage-states.mjs`](./scripts/audit-storage-states.mjs)) — сущность со скрытием без пары `archive`/`restore` и без экрана, а заодно чтения мягких таблиц, оставшиеся без условия живости. Гонять перед закрытием подфазы, как `make audit-fields`.
  - **Почему это запрет:** в 2.9.3 нашлись четыре списка «Акцента» подряд, где «убрать из списка» было дорогой в один конец, а у привычек пункт вообще назывался «Удалить» и делал архив. Дефект живёт на стыке слоёв: бэк «мягко удалил», фронт «спрятал», и оба честны.
- ❌ **Физическое удаление мимо слоя 5** ([ADR-0068](./docs/decisions/0068-deletion-belongs-to-storage.md)). Удаление — дело хранилища: домен зовёт `delete()` и считает, что удалил. `ON DELETE CASCADE` в базе нет ни одного: каскад наш, рекурсивный, по карте владения в `database/core/deletion-graph.ts`.
- ❌ Стейт-менеджеры на фронте (NgRx и пр.) — только Signals + поля класса + rxjs/сервисы при необходимости.
- ❌ `any` в TypeScript. Если тип неизвестен — `unknown` и сужение.
- ❌ ПДн (ФИО, паспорт, реальный email без явной согласия+цели) в БД — см. [`docs/152fz.md`](./docs/152fz.md). Юзеры идентифицируются псевдонимом и логином.
- ❌ **Поле, которое человек заполняет, но нигде не видит** (write-only field). Заводя такое поле, назови экран, где оно вернётся человеку; не можешь назвать — поле не заводим. Отложка допустима, но **явная**: строка в `ALLOW` детектора с причиной или TODO-маркер с этапом.
  - **Проверяется машиной, а не памятью:** `make audit-fields` ([`scripts/audit-write-only-fields.mjs`](./scripts/audit-write-only-fields.mjs)) сверяет поля `*View` бэка с упоминаниями во фронте и печатает те, у кого потребителя нет. Гонять **перед закрытием подфазы**. Инструмент сигнальный: он показывает, куда смотреть, решение — за человеком.
  - **Почему это запрет, а не пожелание:** в 2.7.2 нашлись три таких поля подряд, и все — про доверие, а не про верстку. Продукт **спросил у человека личное и не вернул обратно**: «ради чего откажусь» вообще требуют заполнить при взятии цели в фокус, и это не показывалось нигде. Дефекты этого класса живут на стыке шагов «бэк: поле» и «фронт: форма» — оба шага закрываются честно, а показать никто не обязан.
  - **Зелёный `tsc` тут не помощник** — он не проверяет шаблоны Angular: сборка бывает зелёной при нерабочем экране (поймано в том же заходе). Доказательство — только живой прогон.

## Когда обращаться к человеку

Спрашивать, а не угадывать, если:

1. Новая сущность не описана в [`docs/domain-model.md`](./docs/domain-model.md).
2. Изменение, ломающее API.
3. Новая внешняя зависимость — сначала проверить, нет ли уже похожей в стеке.
4. Появился новый внешний источник для «вдохновения» — брать **только идеи**, в доку писать с нуля под наш scope; не копировать схемы/DTO/миграции/формулировки напрямую.
5. Вопрос про юрисдикцию / ПДн / соответствие 152-ФЗ — никогда не решать самому.
